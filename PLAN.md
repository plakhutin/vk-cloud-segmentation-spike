# Минимальный spike сетевой сегментации VK Cloud

## 1 Цель и границы

Проверить на одном небольшом стенде, что выбранная связка облачных security groups и Kubernetes NetworkPolicy позволяет разделять компоненты проекта и контролировать ingress и egress отдельных приложений в pod.

Результат — применённые конфигурации, таблица проверок с подтверждающими выводами команд и короткий ответ: работает ли выбранный вариант, какие ограничения обнаружены. Подтверждённый отрицательный результат также завершает spike.

Проверяем одну конфигурацию, IPv4, TCP-потоки приложений и необходимый DNS. Для проверок используются обычные непривилегированные pod и тестовые данные. После переноса pod проверяем результат в готовом состоянии.

В этот spike не входят HA, производительность, production hardening, сравнение CNI, FQDN-фильтрация, отдельный egress gateway/proxy/firewall, приватная сеть S3, IPv6, компрометация node, отказы и рестарты CNI, доказательство отсутствия стартовых окон. Эти направления не нужно проектировать заранее или считать блокерами текущего результата.

## 2 Правило для оркестратора

Оркестратор читает план и отчёты, декомпозирует работу, определяет зависимости и допустимый параллелизм, запускает воркеров и сообщает результат пользователю.

**Все технические действия выполняют воркеры:** чтение репозитория и документации, написание файлов, команды, создание ресурсов, настройка, тестирование, интеграция и исправления. Оркестратор самостоятельно эти действия не выполняет.

Для поручения достаточно указать цель, входные данные, область изменений и ожидаемый результат. Достаточно обычного списка задач; схемы контрактов, специальный runtime и реестр блокировок не требуются. Воркеры проверяют собственную работу; один независимый reviewer проверяет итоговые выводы. Отдельная приёмка каждой задачи не нужна.

## 3 Минимальная инфраструктура

Сохраняем ранее выбранные роли, чтобы проверять нужные границы и не тратить spike на оптимизацию количества VM.

| VM | Количество | Ориентир на одну VM |
|---|---:|---|
| Bastion | 1 | 1 vCPU, 2 ГБ RAM, 20 ГБ диска |
| Admin | 1 | 1 vCPU, 2 ГБ RAM, 20 ГБ диска |
| Kubernetes control plane | 1 | 2 vCPU, 4 ГБ RAM, 30 ГБ диска |
| Kubernetes worker | 2 | 2 vCPU, 4 ГБ RAM, 30 ГБ диска |
| PostgreSQL | 1 | 2 vCPU, 4 ГБ RAM, 30 ГБ диска |

Это оценка для тестовой нагрузки: выбрать ближайшие доступные flavors, без отдельного исследования стоимости.

Дополнительно:

- Одна зона доступности и три приватные сети: management, kubernetes, database.
- Один router, SG по ролям и необходимая внешняя связность.
- Один provider LB, один listener и один тестовый backend-сервис.
- Один тестовый S3 bucket с объектом, доступ через публичный HTTPS endpoint.
- Публичные адреса bastion и LB; у остальных перечисленных VM Floating IP нет.

Одна PostgreSQL VM представляет сетевую границу DB-кластера; репликация и failover не проверяются.

В Kubernetes достаточно CNI, штатного DNS, двух диагностических pod A/B и HTTP echo-сервиса. Для входящего пути использовать LB → NodePort Service → echo. Отдельный ingress-controller для этого эксперимента не требуется; результат не распространяется на его поведение.

Для проверки интернет-egress сначала использовать уже доступный работающий внешний HTTPS endpoint. Новую VM-приёмник создавать только если без неё нельзя получить однозначный результат. Серверные журналы полезны, но не обязательны при наличии контрольного успешного запроса и подтверждения блокировки CNI. Внешнее назначение должно быть доступно через внешний путь стенда, без общей приватной маршрутизации.

## 4 Технические решения без отдельного исследования

Использовать принятые в проекте инструменты. Если исходного решения нет, взять один простой вариант: Terraform для облака, kubeadm/containerd и Cilium. Настройку VM выполнить существующими Ansible-ролями либо небольшими скриптами; универсальные модули и роли не разрабатывать.

Зафиксировать использованные версии и сетевой режим. Проверить совместимость выбранных версий и адресные пересечения; сравнение альтернатив не проводить. Стандартные параметры менять только для устранения конкретного препятствия.

Для диагностики достаточно событий CNI и доступных средств на node. Hubble Relay/UI, отдельный стек мониторинга и хранилище телеметрии не разворачивать.

Terraform state вести существующим способом либо локально у одного исполнителя с сохранением файла. Специальный remote backend ради spike не создавать. Секреты и state не включать в общий отчёт.

## 5 Этапы выполнения и параллелизм

| Этап | Что делает воркер | Когда можно начинать |
|---|---|---|
| 1. Уточнить входы | Читает инструкции проекта, определяет VK project/region/AZ, доступы, квоты, CIDR, версии и внешнее тестовое назначение. Записывает короткую схему и ожидаемые потоки | Сразу |
| 2. Подготовить стенд | Инфраструктурный воркер создаёт VM, сети, SG, LB и S3. Параллельно Kubernetes-воркер готовит установку, manifests и команды проверок | После определения необходимых входов |
| 3. Настроить компоненты | Один воркер настраивает доступ через bastion/admin и PostgreSQL; другой устанавливает Kubernetes/CNI. Затем применяет политики и запускает A/B и echo | После готовности соответствующих VM и доступа |
| 4. Провести проверки | Назначенный воркер выполняет таблицу из раздела 7 и сохраняет результаты | После готовности компонентов и фиксации правил |
| 5. Проверить вывод | Независимый reviewer читает результаты; повторяет только неоднозначные проверки. Исполнитель исправляет обнаруженные ошибки в пределах spike | После первого прогона |
| 6. Завершить | Воркер дописывает краткий вывод и выполняет согласованный keep/teardown, сохранив результаты | После последней проверки |

Этапы — основа для декомпозиции, а не требование создавать шесть разных агентов. Достаточно двух исполнительных потоков и одного итогового reviewer; при меньшем числе слотов выполнять последовательно.

Практические правила:

- Один воркер выполняет Terraform apply. После timeout он сначала устанавливает исход операции.
- Разные воркеры не меняют одновременно общие сетевые ресурсы, Kubernetes-политики или одни и те же файлы.
- Во время проверок правила не меняются; перенос pod выполняет тот же проверяющий воркер как отдельный шаг.
- Если проверка выявила проблему, исправлять её и повторять затронутые случаи. Полный повтор без причины не нужен.
- Если неизвестных данных недостаточно для следующего шага, оркестратор задаёт конкретный вопрос; независимая подготовка продолжается.

## 6 Минимальная настройка политик

До тестовых приложений применить default-deny ingress/egress в тестовом namespace и явные разрешения. Разрешить необходимый доступ к кластерному DNS.

Подготовить такие права:

| Поток | Ожидаемый результат |
|---|---|
| A → echo | Разрешён |
| B → echo | Запрещён ingress-политикой echo; egress B к echo разрешён для этого теста |
| A → PostgreSQL, S3, выбранный внешний HTTPS endpoint | Разрешён |
| B → те же PostgreSQL, S3 и внешний endpoint | Запрещён egress-политикой |
| A/B → используемый DNS | Разрешён |
| Pod → management и неразрешённые внешние назначения | Запрещён |
| LB → NodePort → echo | Разрешён выбранный путь |

На облачном слое явно задать SG и их привязки, проверить автоматически созданные разрешения. Для VKCS учитывать delete_default_rules и full_security_groups_control согласно используемой версии provider. Не оставлять случайные default SG или правила, добавленные только для обхода неисправности.

Для основных pod-egress проверок SG должны пропускать проверяемый путь, чтобы облачная блокировка не маскировала отсутствие CNI enforcement. Для отдельного SG-теста использовать соединение между VM без CNI на пути.

Для LB записать фактические источники запросов и health checks и разрешить нужный backend-порт. Не предполагать заранее, какой source IP увидит pod после NodePort/NAT. Этот эксперимент проверяет выбранный путь LB и SG; pod-ingress проверяется отдельно клиентами A/B.

Служебный трафик node, необходимый для установки и работы кластера, допускается отдельными явными правилами. Полный контроль host-egress не является целью spike.

## 7 Минимальный набор проверок

| № | Проверка | Что подтвердить |
|---|---|---|
| 1 | Административный путь и облачная граница | Доступ через bastion → admin к нужным приватным endpoint работает. Admin → PostgreSQL TCP/22 работает, bastion → тот же IP:22 блокируется SG |
| 2 | Входящий путь | Запрос через LB доходит до echo; health checks работают. Один заранее заданный прямой путь в обход LB блокируется |
| 3 | Pod-ingress | A проходит к echo, B блокируется при размещении клиента и echo на одном и разных worker. Egress клиентов к echo разрешён |
| 4 | Pod-egress | A и B на одном worker обращаются к одному внешнему TCP IP:port: A проходит, B блокируется CNI. Для A дополнительно проверяется живое назначение вне allowlist |
| 5 | PostgreSQL | A выполняет SQL, B блокируется сетью. Записать inet_client_addr() для успешного запроса |
| 6 | S3 | A получает тестовый объект, B блокируется сетью. Использовать рабочие credentials; сохранить фактические IP endpoint |
| 7 | DNS и management | Кластерный DNS работает по UDP/TCP; неразрешённый внешний resolver и выбранный management-порт недоступны из pod |
| 8 | Перенос pod | Пересоздать A/B на другом worker, дождаться готовности и повторить внешнюю egress-пару и доступ к PostgreSQL |

Для проверки №2 выбрать реальный источник, имеющий маршрут к NodePort, например admin VM, и живой backend. Недоступность приватного IP из интернета сама по себе не доказывает действие SG.

Достаточные правила доказательства:

1. Перед отрицательной пробой подтвердить доступность того же назначения разрешённым клиентом. Если для этого нужна временная контрольная конфигурация, применить её отдельным шагом, вернуть итоговые правила и затем выполнить проверку.
2. В сравнении A/B использовать одинаковый destination IP, протокол и порт; одинакового DNS-имени недостаточно. Для HTTPS сохранять правильный hostname/SNI.
3. Для основного egress-теста получить событие блокировки CNI либо другой однозначный контрольный эксперимент. Одного timeout недостаточно.
4. Использовать новые соединения. HTTP 403, ошибка пароля или сертификата не доказывают сетевую блокировку.
5. Если DNS намеренно запрещён, проверять прикладное соединение по известному IP, чтобы не измерять только DNS.
6. Для S3 допустим снимок IP на время прогона. Этот результат не подтверждает сопровождение меняющихся DNS-адресов.

Результат каждой проверки: PASS, FAIL или INCONCLUSIVE с короткой причиной. При неполных данных не записывать PASS.

## 8 Что сохранить и когда остановиться

Достаточно файлов, реально использованных для создания стенда, настройки Kubernetes и политик, короткого README с запуском/удалением и results.md с таблицей:

**источник и node → фактический адрес/порт → ожидаемый результат → полученный результат → вывод команды или существенное наблюдение.**

В results.md записать использованные версии, важные параметры CNI/SG, измеренный source IP и ограничения. Сохранять только нужные для вывода журналы. Собственный test framework, схемы evidence, ADR, отдельные контракты, CI/CD и набор runbook не создавать. Небольшой скрипт повторяющихся проверок допустим, если он сокращает работу.

Spike завершён, когда восемь проверок дали понятный ответ или обнаружено конкретное препятствие, достаточное для решения о следующем шаге. Непроверенное явно отметить. Итог отвечает на три вопроса:

- Работает ли выбранная сегментация для проверенных потоков?
- Что не получилось или осталось неподтверждённым?
- Какой один следующий шаг нужен, если он нужен?

Не продолжать улучшения после получения этих ответов. Не начинать новый вариант архитектуры или дополнительную ветку исследования без отдельной задачи. Исправление ошибки настройки допустимо; построение production-решения в завершение spike не требуется.

После сохранения результатов и итоговой проверки оставить либо удалить тестовые ресурсы согласно условиям запуска. Указать, какие ресурсы остались. Оркестратор поручает завершение воркеру.
